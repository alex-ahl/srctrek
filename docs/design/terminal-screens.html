Milestone 7 · changes with the screens

srctrek terminal screens

What trek shows in the terminal: the landing page, a change's screen in every state its trek can be in, settings, the build view while an agent works, the route map of a whole trek, and stepping for editors without a plugin. Text, dim text, and the background are the terminal's own; the colours of states and the accent are srctrek's once the terminal reports its background, and each state has a symbol of its own.

1. Where trek opens

The landing page lists the changes; a change's screen is that change and its trek, built there and stepped from there.

trek ──▶ landing page ──enter──▶ a change's screen ──enter──▶ stepping
◀───esc──── ◀────q─────
trek <range or branch>, trek <pull request URL>, trek --code open that change's screen
S settings, from the landing page

2. The landing page

What's yours, each with its trek's state: your work (the branch checked out, then its uncommitted work, your own open pull requests, and those waiting on your review), your branches (those with a commit of yours the base doesn't have, latest first, the first 8), and the code as it is. Every other pull request and branch is on a view of its own that p and B open, as treks whose change is gone (merged, or its branch deleted) are on d; typing narrows a view, esc clears what's typed, then goes back. The title bar names what the changes are measured against, once. The changes make one table across the row, up to 120 columns: each row the change's name, what it holds, dimmed, and its trek's state, with when the trek was built where there's room. Groups sit under their names, dim, at the left, their rows set in under them. A pull request's trek state comes from its head as listed, the list read again each minute; without gh, the pull requests say why. The selection starts on your branch, even with nothing on it yet. Left open, the rows follow commits, branch switches, and treks saved by an agent; the selection stays where it is. Enter opens the selected change's screen. a slides up every repo beside this one from the bottom, those with work first, the changes dimmed above with the selected one still marked: space adds a repo to go along with the change, → opens its branches, typing narrows them by name or path, esc clears what's typed and then is done, and the title bar then names the repos added. The footer gives up keys from its end where they don't fit; ? lists them all, settings among them.

From 110 columns, the list sits beside the selected change's own screen, the same as it shows on its own: the list keeps to each change's name, ⚑ after a pull request waiting on your review, and its trek's state as a symbol; what a change holds and its trek's overview are on the right. Every change listed is worked out in the background and kept, so moving the selection changes the right side at once; one not worked out yet keeps the last one shown, then says it's opening when that takes a while. The change's keys work from the list: ↵ steps its trek, or builds it when it has none; e steps it in your editor, b builds, y adds a repo the agent proposes and x dismisses it, l opens its builds. Code as it is lists its ways in, and ↵ opens them to choose one. The footer leads with the change's keys, then the page's. Narrower, the list is the page, as below, and enter opens the change's screen.

3. A change's screen, by state

The change on top, the same in every state: what it is, and how big. Under it, its trek. Once there's a trek, its overview shows here and enter steps it, where the Step in setting says; the other place is one key away. A build started with b shows here, its steps as they arrive and a repo the agent proposes, to add with y or dismiss with x; l opens its builds. A trek an agent saves from its own chat shows once it's saved. b always builds the trek: builds it, updates it, or builds it again. Beside the landing page's list, the screen is the same, its keys working from the list.

4. Settings

S opens settings over the list: each setting and its value, with a note beside it when an environment variable sets it. Enter changes the selected one. Everything is kept per user, in $XDG_CONFIG_HOME/srctrek/settings.json (else ~/.config); an environment variable overrides the file, for scripts and CI.

y on the agent copies a one-line request to paste into the agent's chat, through the terminal's clipboard; a terminal that doesn't take it shows the line to copy by hand. The agent then sets the command itself through srctrek's MCP server, which it has registered to build treks (set_agent_command, with the command that runs it headless); srctrek saves it to the settings file, and settings shows it within a couple of seconds. Once a command is set, trek runs it once with a tiny instruction, and settings shows works or the error, before a real build fails on a typo.

Build automatically toggles with enter, off by default: off, a change with no trek waits for b; on, trek starts building it as soon as it opens, when an agent is set.

5. The build view

Opened from a building trek. The overview as soon as the agent starts the trek, steps as they arrive, rejected rounds with their problems, and what the agent is reading.

6. The route map

The whole trek at once: one lane per repo, steps in the order they run, hops crossing between lanes, flags where they are. Enter opens the selected step in the editor; the map is the overview no single editor window can give.

7. Stepping without an editor plugin

The step view drawn in the terminal, for editors without a plugin: the code with the step's lines, narration, values, and signs, the call stack beside it. e opens the step in the user's editor at its line.

Decided

  1. Settings on S.
  2. The agent sets its own command from its chat, through srctrek's MCP server; typing it stays possible, and a test run says whether it works. No list of agent tools: srctrek would have to know each one's flags.
  3. An environment variable overrides the settings file, and settings says so beside the value.
  4. Build automatically is off by default: an agent run costs, so it starts on b unless the user turns this on.
  5. A colours setting: srctrek's state colours, or the terminal's own.
  6. The no-agent state points to settings.
