Add steps to the trek, in execution order from trigger to outcome. Each step is a stop in one file:

- `id`: executed steps in order as "s1", "s2", …; a context step takes the id of the step it explains plus a letter, as "s8a" and "s8b" for s8.
- `repo` (a name from open_change), `file`, `start_line` and `end_line` (the lines this stop covers, numbered as read_file shows them).
- `kind`: call (execution enters a function from the step in `from`, also when reached from a return statement), return (execution comes back, bringing a value, to a function a step still on the call stack showed: the caller, or one further out, carrying on after its call, also when a response from another process comes back to the caller awaiting it), hop (it crosses to another process or repo, or runs later: a request, a message, a job, an event or click handler, a timer, a callback registered earlier; the call stack starts over), or context (code read to understand, not executed). The reader sees a call stack built from these, so a value handed on to another function is a call, not a return.
- `name`: the function, method, route, or handler the step shows, as the code names it ("createRefund", "POST /refunds"); for a step that receives a request, its route. Code with no name of its own (an anonymous callback, a listener, an entry in a key map) is named by what fires it and where it lives ("#save click handler", "l key in App"); never a bare file name, key, or event. The reader follows the flow by these names in the call stack and the route.
- `summary`: the narration the reader reads at each stop, two or three short sentences at most: what happens and why it matters for the scenario, how it follows from the previous stop, any background code that explains it, with the reason to look, and on a step that crosses a contract, the term in it that matters. `details`: what the reader doesn't need to follow the story, such as other paths, edge cases, and what a guessed link assumes.
- `from`: the id of the earlier step execution came from; absent on the first step. Never a context step.
- `for`: on a context step, in place of `from`: the id of the step it explains.
- `via`: the evidence for arriving here, as `{ cites: [{ repo, file, line }], guessed, through }`: the call site, route, config line, message name, or spec entry; on a context step, the line of the step it explains that uses this code. A name shared by both sides (a message topic, a URL path) proves the link when both sides are cited; mark `guessed: true` only when nothing cited proves it, and say in `details` what to compare. A call through a lookup (a handler list, a registry, an interface) cites both the call site and where this target is registered or picked. When `from` or `for` is in another repo, cite both repos or mark the link guessed. On a hop, `through` says what carries it and from where, in a few words that read after ↯ in the route: "via the agent", "on a timer", "on the next render", "POST from the app", not a bare protocol like "HTTP"; only a hop has it. `null` only on the first step.
- `trivial`: true for a step worth skipping. `uncertain`: `{ severity, note }` for a risk the reader should know (high: likely wrong behaviour; medium: risky; low: worth knowing).
- `predicted_values`: `{ name, value, line, role, uncertain? }`, role argument, assignment, or return, each on a line inside the step. Use the example scenario's values and keep their names the same across steps, so the reader can follow one value from where it's made to where it's used. Give values first to what decides where the flow goes (the branch taken, the handler picked), then to what it carries on (which record, which amount), each as short as the reader needs it, setup lines included; leave out values that only restate the code, such as a field passed straight through or a default left as it is. Mark a value you doubt `uncertain`.

Every line a step relies on (its first and last line, each citation, each value's line) is checked against the code: it must exist and not be blank. Steps are added all or none: when any has a problem, every problem comes back and nothing is added. Sending a step with an id already in the trek replaces it.
