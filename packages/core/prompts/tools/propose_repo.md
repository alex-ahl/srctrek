Propose a repo the route leads into that the change doesn't include, such as a service the code calls or a consumer of a message it sends. Give `{ name, source?, reason, evidence }`: `name` is what the code calls the service; `reason` says in a sentence what leads there; `evidence` is `[{ repo, file, line }]`, the lines that show it, such as a client, a config value, or a contract file. Every evidence line is checked against the code.

`source` is where git can get the repo: a path relative to the current repo, or a URL. Find it before proposing: first among the repos open_change lists as next to this one, then on the code host with your own tools, if you have them, starting with the organisation in the current repo's remote. When you can't find it, leave `source` out and propose anyway: the user gives the location when they add it. When the change is a pull request, read its description with your own tools, if you have them, for links to companion pull requests in other repos, and propose each of those repos with its pull request's branch: `<url>@<branch>`.

With a source, the repo is opened at once: on the branch this work is on, as part of the change, when it has one; else at its default branch, or at the revision a source ending in `@<revision>` pins. The answer says which, and what to flag when it's in doubt. Read it with the read tools and carry the trek on into it. The user decides afterwards whether to keep it on the repos list. Without a source, or when it can't be opened, end that hop at the boundary and say where the route goes next.
